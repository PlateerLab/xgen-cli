# 두 파일·22KB 소스·응답 범위 비교

2026-10-05에 48회 실제 API 비교를 마쳤다. 현재 프로필에서 파일 전체를 모델의 최종 summary로 복사하는 방식은 큰 소스에서 한계가 있었고, 조건부 재확인 지시도 안정적으로 인용을 보장하지 못했다. 등록한 판정은 `do_not_adopt_response_boundary`이며 기본 prompt·엔진·개인 설정은 변경하지 않았다.

## 조건

Python·Node 두 작업군에서 각각 두 파일을 수정했다. 작은 소스 총량은 250/231바이트, 큰 소스는 22,582/22,563바이트다. 같은 함수 로직에서 보존해야 하는 상수 데이터를 늘린 합성 fixture이며 실제 대형 저장소를 대표하지 않는다. 원래 상수·테스트·설정을 보존하도록 계약과 hidden 검증에 명시했다.

각 작업군에서 작은/큰 파일, 전체 소스 인용/검증 요약을 교차해 8개 조합을 만들었다. 기존·항상 재확인·인용 시에만 재확인을 각각 2회 반복했다. 같은 binary와 DeepSeek `deepseek-flash` profile, inference limits, 승인 후 resume 방식을 사용했다. 조건 순서는 교대했고 자동 재시도는 없었다. 입력·후보·생성기·평가기 SHA256을 실행 전후 확인했다.

사전 기준은 모든 조합에서 조건부 후보가 요청한 응답을 충족하고 회귀하지 않으며, 두 작업군에서 인용 개선이 나오는 것이다. 인용의 평균 호출·total tokens 증가는 25%, 요약은 5%, driver 시간은 30% 이하를 요구했다. 요약에서는 항상 재확인보다 token을 덜 써야 한다. 결과에 맞춰 기준을 바꾸지 않았다.

## 기능·완료·인용 결과

| 작업 | 기존 | 항상 재확인 | 조건부 재확인 |
| --- | ---: | ---: | ---: |
| 작은 두 파일 전체 인용 일치 | 0/4 | 4/4 | 2/4 |
| 22KB 두 파일 전체 인용 일치 | 0/4 | 0/4 | 0/4 |
| 전체 인용 요청에서 durable completion | 6/8 | 4/8 | 7/8 |
| 요약 요청에서 durable completion | 8/8 | 8/8 | 8/8 |
| 요약의 명령·변경 파일 내용 일치, 별도 감사 | 8/8 | 8/8 | 8/8 |

48회 모두 실제 수정 파일의 visible·build·hidden 검증과 원래 테스트·설정 보존을 통과했다. 기능 수정 성공을 요청한 최종 응답의 성공과 혼동하지 않는다. 완료한 41회는 offline replay에서 같은 summary를 반환하고 journal·usage DB 바이트를 유지했다. journal을 다시 대조해 Unknown과 동일 effect의 중복 실행 시작은 모두 0이었다. usage도 48회 모두 완전했다.

전체 인용 요청의 24회 중 7회는 `model_rejected.output_truncated`로 최종 완료 출력이 없었다. 큰 Python 기존 2회, 큰 Python·Node 항상 재확인 각 2회, 큰 Node 조건부 1회다. 파일 수정 단계의 실패나 이미 확정된 답변의 허위 인용으로 분류하지 않는다.

큰 파일에서 완료된 나머지 5회도 요청한 전체 소스를 생략했다. 기존 Node 2회, 조건부 Python 2회·Node 1회다. 완료 이벤트만으로 사용자 출력 계약이 충족됐다고 판단할 수 없다는 사례다. 작은 조건부 Node 2회는 코드 블록을 제공했으나 실제 파일과 불일치했다. 작은 Python 조건부 2회는 정확히 인용했지만 모든 파일을 검증 후 native read-text로 다시 읽었다는 관찰은 없었다. 지시와 실제 관찰·결과를 구분한다.

## 형식과 사실 정확도의 분리

작은 Node 조건부 2회의 답변 코드도 별도 복사본에서 visible·hidden 검증을 실행했다. 1회는 수정 전의 `flat(2)`와 `Array(count).fill(items).flat()`을 그대로 보여줘 두 검사 모두 실패했다. 실제 수정 파일의 검사는 통과했으므로 최종 응답에 오래된 버그 코드를 내보낸 사례다. 다른 1회는 동등한 구현을 재작성했고 두 검사를 통과했다. 인용 불일치를 전부 단순 서식 차이나 전부 기능 오류로 묶지 않는다. `quoted-code-review.json`에 분류를 보존했다.

등록한 출력 계약은 정확히 하나의 `json` 코드 블록을 요구했다. 요약 24회는 모두 코드 블록 없이 raw JSON을 반환해 원래 형식 검사에서 실패했다. 이 원본 점수와 채택 판정을 그대로 보존했다.

실행이 끝난 뒤 추가 내용 감사에서 표준 `json.loads`로 응답 전체가 raw JSON인지 확인했다. 임의 부분 문자열을 추측해 추출하지 않았다. 같은 field schema로 명령 argv·exit code·순서를 process output·invocation recipe와 대조하고, 변경 파일을 실제 작업 전후 바이트와 비교했다. 요약 24회의 내용은 모두 일치했다. 이 별도 감사는 사후 분석이며 채택 기준을 통과한 것으로 재해석하지 않는다. 모든 자연어 설명의 자동 사실 검증도 아니다.

## 토큰과 시간

요약 작업만 비교하면 다음과 같다. 세 조건 모두 8회 완료했고 내용도 일치했으므로 실패로 짧아진 응답과의 비용 비교를 피했다.

| 조건 | model 호출 합계 | total tokens 합계 | 평균 driver 시간 |
| --- | ---: | ---: | ---: |
| 기존 | 69 | 795,183 | 11.60초 |
| 항상 재확인 | 79 | 953,862 | 13.03초 |
| 조건부 재확인 | 72 | 812,424 | 12.13초 |

항상 재확인은 기존보다 tokens 20.0%, 평균 driver 시간 12.3%를 더 썼다. 조건부는 기존보다 tokens 2.2%, 시간 4.5% 증가했고 항상 재확인보다 tokens 14.8%를 덜 썼다. 전체 평균으로 조건별 한도를 통과했다고 주장하지 않는다. 작은 Node 요약에서는 조건부 호출이 8→9, tokens가 54,702.5→62,422.5로 늘어 해당 조합의 5% 한도를 넘었다.

같은 작업의 큰/작은 소스를 비교하면 요약의 평균 tokens는 Python 기존 약 2.46배·항상 약 2.26배·조건부 약 2.31배, Node 기존 약 2.52배·항상 약 2.50배·조건부 약 2.29배였다. 이 배수는 보존 상수 데이터를 확대한 합성 workload의 관측치다. 소스 크기만으로 실제 저장소의 비용·시간을 예측하는 공식은 아니다.

driver 시간은 초기 실행과 승인 후 resume를 포함하고 독립 테스트·replay는 제외했다. provider 호출 시간 합계도 원본 report에 있다. 캐시 토큰을 total에 더하지 않았으며 가격 설정이나 금액·통계적 유의성 주장은 없다.

## 판단

조건부 prompt는 작은 두 파일에서도 인용을 안정적으로 보장하지 못했고, 큰 전체 인용은 모든 조건에서 실패했다. 기본 적용하지 않는다. 요약에 무조건 전체 파일을 다시 읽게 하면 이 표본에서는 보고 내용 개선 없이 비용을 늘렸다.

다음 개발 검토 대상은 모델이 파일 전체를 최종 summary 안에 다시 생성하게 하는 요구 자체다. 사용자에게 보여줄 인용을 실제 파일·관찰 digest에 연결하는 방법과, 응답 출력 상한을 넘는 경우의 표현을 별도 계약으로 설계해야 한다. 이 실험에서 프로필 상한을 높이거나 파일 인용을 새 아티팩트로 바꾸는 제품 변경은 하지 않았다.

재현과 합성 fixture의 한계는 `evals/response-scaling/README.md`에 있다. `results/2026-10-05/`에는 원본 report, 원본 답변, 사후 내용 감사, 실행 당시 source snapshot을 보존했다. 원본 Run DB와 credential은 공개하지 않았다. 사후 감사 명령은 다음과 같다.

```sh
python3 scripts/audit-response-scaling.py /tmp/xgen-response-scaling-...
```
