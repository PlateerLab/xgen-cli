# 최종 응답 일치 평가 — 2026-10-04

이전 실사용에서 할인 코드는 올바르게 수정됐지만 최종 응답에 다른 수식이 적힌 사례가 있었다. 이를 한 사례에
맞춘 prompt 변경으로 처리하지 않고, 일반적인 평가 도구와 서로 다른 fixture로 다시 확인했다.

## 방법

- 실제 DeepSeek `deepseek-flash`, `json_object`, thinking disabled를 사용했다.
- 설계 사례: 할인율·온도 변환. 별도 검증 사례: 평균·범위 제한. 고객 코드 대신 작은 Python 예제를 사용했다.
- 각 사례를 독립된 workspace/Run에서 3회씩 실행했다. 최종 코드 블록을 요청하는 방식과 일반 설명을 요청하는
  방식으로 각각 12회, 총 24회를 관찰했다. 모델과 별도로 테스트를 실행하고 테스트 파일 변경 여부를 확인했다.
- 코드 인용은 AST로 비교하고, 자연어와 수정 전·후 설명은 실제 파일·tool output·독립 테스트와 대조했다.
  독립 검토 초안도 사용했으나, 오류 후보와 비정형 설명은 로컬 기록을 다시 확인했다.

## 결과

| 사례 | 코드 블록 요청 | 일반 설명 요청 | 독립 테스트 |
| --- | --- | --- | --- |
| 할인율 | 3회 | 3회 | 각 3개 통과, 테스트 파일 변경 없음 |
| 온도 변환 | 3회 | 3회 | 각 3개 통과, 테스트 파일 변경 없음 |
| 평균 | 3회 | 3회 | 각 3개 통과, 테스트 파일 변경 없음 |
| 범위 제한 | 3회 | 3회 | 각 3개 통과, 테스트 파일 변경 없음 |

24회 모두 작업 완료가 저장됐고, 확인한 최종 변경 설명은 실제 구현과 일치했다. 이전에 관찰한 잘못된 수식은
이번 평가에서 재현되지 않았다. corpus가 작고 실행 횟수도 제한적이므로 문제가 해결됐다는 의미는 아니다.

초기 평가기는 수정 전 코드까지 최종 코드처럼 비교해 오탐을 만들었다. 실제로 다른 인용을 확인해 보니 수정
전·후를 명시한 정상 설명이었다. 수정한 평가기는 `mixed_quotes`/`needs_review`로 검토 후보를 표시하며,
인용 차이를 곧바로 거짓 주장으로 판정하지 않는다. 이 해석은 두 종류 이상의 함수로 회귀 테스트했다.

완성된 평가 도구는 네 사례를 한 번씩 추가 실행해 결과 수집·독립 테스트·새 quote 분류를 확인했다. 이는 도구
검증용 4회이며 모델 개선의 측정으로 합산하지 않는다.

## 원인 후보와 결정

수정 이후 최종 파일 내용을 read-text로 다시 관찰한 기록은 없었다. 현재 PlanningContext는 invocation
arguments를 전달하지 않고 write/apply-patch output은 path·digest·크기·편집 수를 전달한다. 따라서 다음 model
turn은 실제 최종 코드 대신 이전 파일 관찰과 테스트·write metadata로 설명을 구성할 수 있다.

이는 확인된 정보 경계이지만, 그 경계가 이전 오류를 일으켰다는 인과 증거는 아직 없다. 서로 다른 입력에서
최종 설명의 실제 불일치가 재현되지 않아 engine, 공유 prompt, output schema는 변경하지 않는다. 현재 변경은
평가 도구·fixture·CI와 검증 기록에 한정한다.

다음에 실제 불일치가 두 종류 이상의 작업에서 확인되면 마지막 파일 관찰 등 일반적인 개선을 비교한다. 그때
설계에 사용하지 않은 새 사례를 추가하고 작업 성공·설명 일치·model/tool call 수를 함께 확인한다.

재현 방법과 각 metric의 범위는 [평가 도구 안내](../../evals/final-responses/README.md)를 따른다.

평균·범위 제한 사례도 오탐 조사에 사용한 이후에는 향후 변경의 held-out 결과로 계산하지 않는다. 비교기 자체는
기존 설계에 사용하지 않은 comprehension/helper와 async 함수로 추가 검증했다. API 없이 실행하는 회귀 테스트
9개, Python compilation, release workflow와 public documentation 검사도 통과했다.
