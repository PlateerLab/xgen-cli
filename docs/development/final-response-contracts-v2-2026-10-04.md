# 최종 응답 2차 실험: 인용과 실행 근거

2026-10-04에 명시한 입력 계약과 출력 형식으로 24회 실제 API 비교를 완료했다. 기존의 파일 인용 실패가 두 설계 사례에서 재현됐고, 같은 후보가 새 검증 집합에서도 인용 성공을 늘렸다. 판정은 `promising_requires_larger_validation`이다. 기본 prompt·엔진·개인 설정은 변경하지 않았다.

## 설계와 측정

1차의 별도 검증 사례 `split-last`·`rotate`를 설계 집합으로 이동했다. 새 별도 검증은 CRLF·CR 정규화와 Object.is 기준 인접 중복 제거다. 계약은 빈 입력, Unicode, 순서, 입력 불변성, 허용 값과 경계 동작을 명시하며 hidden 테스트도 그 범위 안이다.

각 사례를 기존·후보 조건에서 3회 반복했다. 후보는 1차의 검증 후 소스 읽기·관찰 내용 그대로 복사 지시와 동일하다. 양쪽 모두 같은 입력 계약과 명령·exit code·변경 파일 JSON 출력 계약을 받았다. 같은 local release binary와 DeepSeek `deepseek-flash` profile을 사용했고 새 workspace·Run에서 실행 승인 중단 후 resume했다. 실패 자동 재시도는 없었다.

실행 전 SHA256과 판정 기준을 등록하고 완료 후 불변을 확인했다. 후보나 fixture를 결과에 맞춰 변경하지 않았다. 설계에서 서로 다른 두 사례의 기존 인용 실패 재현, 양 split 인용 개선, workflow·인용·근거 응답 회귀 없음, 새 검증 집합의 근거 응답 개선, 각 split 평균 호출·total tokens 증가 25% 이하를 요구했다.

근거 응답 성공은 작업 완료·독립 검증과 함께 소스 인용, 명령 기록, 변경 파일 목록이 모두 일치한 경우다. 명령은 실행 output과 step의 invocation recipe를 연결해 argv·exit code·실행 순서를 비교했다. 계획만 있고 실행하지 않은 명령은 인정하지 않았다. 변경 파일은 전후 내용으로 생성·삭제까지 검사했다. Python runtime cache는 제외했다.

호출은 83에서 96으로 15.7%, total tokens는 497,406에서 608,416으로 22.3% 증가했다. 설계 tokens 증가는 21.1%, 새 검증은 23.5%로 각 split의 25% 한도 안이다. 캐시 토큰을 total에 중복 합산하지 않았으며 금액은 계산하지 않았다.

24회 모두 원래 테스트·설정 보존과 독립 visible·build·hidden 검증을 통과했다. offline replay는 같은 최종 summary를 반환하고 journal·usage DB 바이트를 유지했다. journal을 다시 읽어 Unknown과 같은 effect의 중복 실행 시작이 모두 0임을 확인했다.

## 실제 실패와 설명 문장 검토

기존 인용 실패 6회는 split-last 2회, rotate 1회, adjacent-dedupe 3회다. 함수 구현 재작성·변수명·서식 변경이며 계약 안에서 동등한 코드였지만 실제 수정 파일 전체를 그대로 보여달라는 출력 계약을 위반했다. 후보는 모든 실행에서 최종 검증 뒤 소스를 다시 읽고 전체 내용을 일치시켰다.

이 6개 답변의 코드 블록을 별도 검증 복사본에 넣어 visible·hidden 테스트와 build를 다시 실행했고 모두 통과했다. 파일 인용 불일치를 기능 실패로 혼동하지 않기 위한 확인이며 원본 Run·실험 점수는 바꾸지 않았다.

별도의 검토 후보 추출 뒤 실제 파일·응답·명령 기록을 직접 대조했다. split-last 기존 2회는 설명에서도 `rsplit(sep, 1)`로 고쳤다고 했지만 실제 파일은 `rfind(sep)`였다. 단순 서식 차이 외에 구현 방식 설명의 사실 불일치도 있었다. 응답에 명시한 source digest는 실제 파일과 일치했다.

같은 기존 2회는 모델이 수정 전 실패 명령을 실행하지 않았다. 외부 평가기는 초기 실패를 확인했지만 그 관찰을 모델 관찰로 세지 않았다. 두 응답은 실패 명령을 실행했다고 주장하지 않았고 JSON도 실제 성공 명령만 담았다. 명령 보고를 조작한 것으로 분류하지 않으며, 먼저 실패를 관찰하라는 작업 지시를 지키지 않은 별도 한계로 기록한다. 후보 12회는 실패 process 관찰이 있었다.

명령 JSON과 변경 파일 검사만으로 자유 형식 설명 전체의 정확성을 보장하지 않는다. 24개 답변의 구현 설명과 명시한 명령 결과를 직접 검토했으나 이를 범용 자연어 사실 검증기로 확대하지 않는다.
